<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host-shell origin -> embedded tenant-app iframe (CROSS-SITE) | The defining Mode A seam. Two distinct `*.vercel.app` origins (PSL-separated) make this genuinely third-party — ordinary cookies are blocked, so the popup + CHIPS partitioned cookie are required. A same-origin host-shell would forfeit the gate (D-09). |
| popup -> opener (iframe) postMessage | `openAuthPopup` enforces origin + source + namespace via `isTrustedMessage`; a wrong-origin message never resolves `{ code }`. |
| opener fetch -> `/auth/consume` (the seam) | The opaque one-time handle is exchanged for a Partitioned Set-Cookie; the transport (fetch/navigation) is swappable, decided by the Plan 05 live observation. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-08 | Spoofing | opener postMessage receipt | mitigate | `openAuthPopup({ allowedOrigins })` pins the trusted origin allowlist; the package's `isTrustedMessage` enforces origin AND source AND namespace before resolving `{ code }`. |
| T-05-09 | Tampering / Spoofing | cross-site iframe framing | mitigate | The tenant app sets `frame-ancestors` to allow ONLY the host-shell origin (not `*`, not `DENY`) — clickjacking-resistant while still permitting the intended cross-site host (A6). |
| T-05-10 | Information Disclosure | the consume URL carries `?code=` | accept | The opaque one-time handle legitimately appears in the consume URL (exactly like an OAuth auth-code); the session token never does (the package keeps it in `Set-Cookie` only). This upholds the existing THREAT-07 boundary documented in docs/threat-model.md. |
| T-05-11 | Elevation of Privilege | first-party shortcut (hollow gate) | mitigate | The host-shell is a SEPARATE origin so the iframe is genuinely third-party; the demo cannot silently pass on first-party cookies. Acceptance criterion asserts a distinct package/origin. |

Note: this plan authors the opener-drives-consume invocation (the consume-transport seam), which is consume-route-adjacent client wiring. It does NOT modify the package's consume route, cookie-attribute setting, or transferStore behavior — those are consumed unchanged. The live CHIPS observation that becomes the THREAT-06 manual-check evidence (and the D-10 transport decision that may flip the seam) is recorded against docs/threat-model.md in Plan 05, satisfying the threat-model discipline at the point the empirical result is known.
</threat_model>
