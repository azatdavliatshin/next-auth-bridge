<objective>
Prove provider-agnosticism (EXAMPLE-03): a CI job runs a dockerized Keycloak as a generic OIDC provider and drives the bridge mechanics against a real, non-Entra session — catching any accidental Entra-specific coupling. Critically, the session is established via a REAL auth-code + PKCE (S256) flow using a browserless form-walking helper (NOT direct-access-grant/ROPC, which would bypass PKCE and silently void the real-PKCE rationale that justifies Keycloak over a mock provider). The test then drives `/auth/bridge` -> `/auth/consume` to a 302 with a Partitioned Set-Cookie and asserts the handle is one-time (replay -> 4xx, no cookie).

Purpose: The bridge must work against any OIDC provider, not just Entra. This is the CI-automatable half of the proof (the live Entra preview is Plan 05). The real auth-code + PKCE flow here matters because it produces a genuine second-provider OIDC session for the agnosticism proof (and a mock/ROPC would not). NOTE — scope it accurately: this roundtrip does NOT re-prove THREAT-05 (PKCE non-interference). By the time the bridge harvests, the short-lived pkce/state cookies have already been consumed at the OAuth callback and are absent from the session-bearing request, so there is nothing for the harvest to (not-)disturb. THREAT-05 is proven by the Phase 2 decoy-exclusion unit test (the harvest takes only session-token chunks and excludes pkce/state/csrf). Do not cite this Keycloak roundtrip as THREAT-05 evidence — it is provider-agnosticism evidence.
Output: The browserless PKCE login helper, the Keycloak roundtrip test, the pre-seeded realm-export, and the GitHub Actions workflow with a Keycloak service container + readiness poll.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CI -> Keycloak token endpoint | The browserless helper performs a real auth-code + PKCE exchange; using ROPC instead would silently bypass PKCE and falsify the agnosticism claim. |
| Keycloak session -> `/auth/bridge` (mint) | The bridge mints a handle only for a genuinely authenticated (Keycloak) session — re-exercising the session-gate against a non-Entra provider. |
| handle -> `/auth/consume` (redeem) | One-time exchange; replay must fail closed (4xx, no cookie) regardless of which IdP minted the session. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-12 | Spoofing | CI login mechanism | mitigate | The realm-export DISABLES Direct Access Grants and REQUIRES PKCE S256, so the only viable CI login is the real auth-code + PKCE flow — an accidental ROPC pass is structurally impossible. Acceptance criteria grep for the absence of grant_type=password and the presence of S256. |
| T-05-13 | Tampering | handle replay (non-Entra session) | mitigate | The roundtrip test asserts a replayed handle returns 4xx with an empty getSetCookie() — the one-time-use invariant holds against a Keycloak session, catching IdP-specific coupling in the exchange. |
| T-05-14 | Tampering | committed CI secrets | mitigate | Keycloak admin/test-user creds come from GitHub Actions secrets / job env (D-04); the realm-export ships only non-sensitive test fixtures; no real secret committed (acceptance asserts no secrets and no internal IDs). |
| T-05-SC | Tampering | dockerized Keycloak image | mitigate | Pin a known-good Keycloak 26.x image tag (not latest) per RESEARCH A5/Open Question 3; explicit readiness poll instead of trusting the image HEALTHCHECK alone. |

Note: this plan drives the package's existing bridge/consume routes unchanged against a second provider — it does not modify the routes, transferStore behavior, or cookie-attribute setting.
